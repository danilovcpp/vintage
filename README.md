# IT Company in One Codex

**Шаблон виртуальной продуктовой и инженерной команды для нового проекта.** Русскоязычный, переносимый между чистыми Git-репозиториями; не зависит от выбранного языка программирования, UI-фреймворка или предметной области.

## Быстрый старт (2 минуты)

1. Распакуйте **содержимое** архива в корень нового репозитория, сохраняя скрытые папки `.codex/` и `.agents/`. Инициализируйте Git, если он ещё не инициализирован (`git init`).
2. Откройте корень репозитория в Codex CLI / IDE / desktop. Важно запускать Codex **из корня**, чтобы он обнаружил `AGENTS.md` и skills. **Подтвердите доверие (Trust) к своему репозиторию:** без него Codex может пропустить проектные `.codex/config.toml` и custom agents.
3. Отправьте: **`Начни discovery. Моя идея: ...`**. Можно отправить только «Начни discovery» — агент должен начать с вопроса об идее. Альтернативно скопируйте текст из `prompts/01-discovery.md`.
4. Отвечайте на вопросы циклами по 3–5. Отвечать «не знаю», «предложи варианты», «решим позже» разрешено. Агент будет фиксировать решения и открытые вопросы на диске.
5. Для возобновления в другом чате: **`Продолжи проект по workspace/STATUS.md. Предложи следующий шаг и вопросы.`**

**Не требуется** регистрировать внешние API, покупать плагины, запускать сервер, устанавливать Python-пакеты. Python 3.11+ нужен лишь для необязательной локальной проверки целостности (`python tools/validate_setup.py`).

## Как устроена «компания»

- **Engagement Lead / Engagement Manager** — главный агент Codex, управляет проектированием, общается с заказчиком, поддерживает единый источник истины и собирает согласованные версии документов (`AGENTS.md`).
- **Специалисты** — 16 конфигураций в `.codex/agents/*.toml`: бизнес-аналитика, рынок, продукт, архитектура, данные, безопасность, UX, дизайн, backend, frontend, mobile, QA, SRE, delivery и независимый критик. Их можно привлекать как subagents при поддержке среды.
- **Skills** — 13 методик в `.agents/skills/*/SKILL.md`: интервью, рынок, экономика, PRD/SRS, архитектура, UX, roadmap, реализация, качество, review, изменение scope и handoff.
- **Playbooks** — внутренние стандарты и подробные чек-листы; **templates** — скелеты конечных документов; **workspace** — живое состояние именно вашего проекта.
- **prompts** — воспроизводимые команды без зависимости от несуществующих кастомных slash-команд.

## Последовательность работ

| Этап | Цель | Основные артефакты | Решение владельца |
|---|---|---|---|
| 0. Intake | Понять идею, контекст и ограничения | `workspace/PROJECT_BRIEF.md` | Подтвердить понимание |
| 1. Discovery | Итеративное интервью, проблематика и пользователи | `workspace/QUESTIONS.md`, `DECISIONS.md`, `ASSUMPTIONS.md` | Закрыть критические неопределённости |
| 2. Viability | Рынок, конкуренты, экономика, build/buy, риски | `deliverables/02-opportunity-assessment.md` | Go / Pivot / No-Go / Research more |
| 3. Product | Scope MVP, сценарии, измеримые требования | `deliverables/03-product-specification.md` | Утвердить scope |
| 4. Detailed SRS | Детальное техническое задание с приёмкой | `deliverables/04-detailed-srs.md` | Утвердить требования |
| 5. Architecture | C4, ADR, контракты, NFR, угрозы, эксплуатация | `deliverables/05-architecture.md` | Утвердить ключевые ADR |
| 6. UX/UI | User flows, IA, вайрфреймы, токены, состояния, прототип | `deliverables/06-ux-ui-specification.md` | Утвердить основные потоки |
| 7. Delivery plan | Зависимости, вертикальные срезы, milestones, риски | `deliverables/07-delivery-plan.md` | Утвердить этапы/бюджет |
| 8. Readiness | Сквозная проверка и handoff к реализации | `deliverables/08-readiness-review.md` | Разрешить старт реализации |
| 9. Build | Реализация утверждённых этапов, тесты и ревью | `implementation/` и код | Принимать этапы |

**Важно:** исследования могут выполняться параллельно с интервью, но документы до согласования обозначаются `DRAFT`. Никогда не обозначайте `APPROVED` без недвусмысленного ответа пользователя.

## Ключевые правила поведения

- В каждом раунде интервью 3–5 приоритетных вопросов, зачем они нужны, для сложных — 2–3 варианта и рекомендация. Не превращать интервью в анкету на 100 вопросов.
- Отделять **FACT / OWNER_DECISION / ASSUMPTION / RECOMMENDATION / UNKNOWN**, вести ID, ссылки и статус.
- Конкурентов и юридические нормы проверять с указанием даты и источника. При отсутствии web — сообщать о пробеле.
- Настоящие subagents полезны для *независимых read-only экспертиз*. Главный агент объединяет выводы и записывает канонические файлы, не допуская гонок.
- Стек выбирать аргументированно, а не по привычке; обсуждать экономику сложности (в том числе альтернативы «не писать»).
- Без разрешения владельца не создавать рабочий продукт, не подключаться к платным сервисам, не менять инфраструктуру и не отправлять конфиденциальные данные наружу.

## Как передавать результат в следующие чаты

`workspace/STATUS.md` — точка входа: там стадия, решения, блокеры и путь к текущим документам. В новом чате достаточно попросить прочитать его и продолжить. Для существенных изменений используйте `prompts/09-change-request.md`.

## Дополнительные инструменты

Система работает **без дополнительных плагинов**. Полезны по необходимости: встроенный Codex web search для рынка и стандартов; бесплатные **Penpot** / **Figma Starter** для редактируемого UX; **Mermaid**, **diagrams.net** для диаграмм; **Playwright**, **Storybook** для проверки интерфейсов; GitHub для issue/PR/CI. Не устанавливайте всё сразу: актуальная матрица — `references/TOOLS_AND_INTEGRATIONS.md`.

## Верификация

`python tools/validate_setup.py` — проверка структуру, TOML, frontmatter, ссылок. **Это статическая проверка**, а не подтверждение, что Codex уже исполнил каждый workflow. Для ручного smoke-test отправьте в новый чат «Начни discovery» и убедитесь, что вопросы появились, а код не был создан.
